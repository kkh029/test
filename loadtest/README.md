# FPS 서버 부하 테스트

대상: `https://kkh029.duckdns.org/fps/` (nginx/1.24.0 → 게임 서버, WebSocket `/fps/ws`)

## 도구

| 파일 | 내용 |
|---|---|
| `loadtest.js` | 실제 클라이언트 흐름 재현: `POST api/rooms` → WS `join` → `preparing/ready` → 호스트 `start` → 20Hz `state` 전송 |
| `httpburst.js` | 고정 동시성으로 HTTP GET 처리량·지연 측정 |

```bash
npm i
NODE_USE_ENV_PROXY=1 node loadtest.js --rooms 10 --per-room 4 --hold 60 --json results/x.json
NODE_USE_ENV_PROXY=1 node httpburst.js --levels 10,25,50,100 --secs 15
```
(`NODE_USE_ENV_PROXY=1`은 HTTPS 프록시 뒤에서 실행할 때만 필요)

### 측정 지표
- **join ms**: WS 연결 시작 → `welcome` 수신
- **input→snap ms**: `state`의 yaw 값에 마커를 심어 보내고, 서버 `snap`에 그 값이 돌아올 때까지의 시간 (= 네트워크 RTT + 서버 틱 대기 + 처리)
- **snap gap ms**: 서버 스냅샷 수신 간격 (정상 50ms = 20Hz). 서버 과부하 시 간격이 늘어남
- **unexpectedClose**: 테스트 중 서버가 끊은 연결 수 (접속 유지 능력)

## 결과 (2026-11-27, 측정 위치→서버 기본 RTT ≈ 183ms)

### 1. 동시 접속자 한도 — 앱 설정이 병목
| 항목 | 값 |
|---|---|
| 방당 사람 최대 | **4명** (fill=8로 슬롯 8개·봇 해제해도 5번째부터 `full`) |
| 서버 전체 방 최대 | **30개** (초과 시 HTTP 503 "서버에 방이 너무 많습니다") |
| ⇒ 최대 동시 플레이어 | **120명** |

방 수명: 아무도 입장하지 않은 방은 30–60초 내 삭제됨(측정). 반면 매치가 진행된 뒤 전원이 나간(비정상 종료 포함) 방은 그 직후 재실행 시점까지 슬롯을 점유하고 있었음 → 10분 테스트 재실행에서 방 18개(72명)만 생성됨. 정확한 정리 시간은 미측정.

### 2. 부하 단계별 응답 (60–90초 유지)
| 동시 플레이어 | join p50 | input→snap p50 / p99 | snap gap p50 / p99 / max | 끊김 |
|---|---|---|---|---|
| 2 | 1060 ms | 201 / 343 ms | 48 / 66 / 68 ms | 0 |
| 20 | 1000 ms | 209 / 274 ms | 50 / 64 / 286 ms | 0 |
| 40 | 978 ms | 207 / 249 ms | 50 / 65 / 282 ms | 0 |
| 80 | 967 ms | 206 / 254 ms | 50 / 62 / 288 ms | 0 |
| **120 (최대)** | 900 ms | 206 / 255 ms | 50 / 61 / 334 ms | 0 |

→ 최대 인원에서도 지연·틱 안정성 변화 없음. 서버 연산 여유가 큼. 순수 서버 처리 지연 ≈ input→snap − RTT ≈ **20–25ms**(틱 대기 평균 25ms 포함).

### 3. 접속 유지 (soak)
- 120~124명 × 약 6분: 끊김 0
- 72명 × 10분 (snap 87만 건): 끊김 0, snap gap p99 64–66ms, >500ms 1건

### 4. HTTP API (`GET /fps/api/rooms`)
| 동시성 | 처리량 | p50 | p95 | p99 | 오류 |
|---|---|---|---|---|---|
| 10 | 52 req/s | 183 | 187 | 864 | 0 |
| 25 | 134 req/s | 183 | 189 | 211 | 0 |
| 50 | 270 req/s | 182 | 188 | 221 | 0 |
| 100 | 478 req/s | 183 | 198 | 244 | 504 ×18 (0.25%) |
| 150 | ~740 req/s | – | – | – | 0 (재시험) |

처리량은 동시성에 거의 선형 비례 → 포화점 미도달 (측정 클라이언트·프록시 쪽 한계가 먼저 옴).

## 해석 / 권장
1. **실제 상한은 `방 30개 × 4명` 설정값.** 서버 자원은 이보다 훨씬 여유 있으므로 더 받고 싶으면 방 개수 상한을 올리는 것이 우선.
2. **사용 후 비게 된 방의 정리 시점 확인** 권장 — 매치 후 전원 이탈한 방이 한동안 슬롯을 점유함(미입장 방은 1분 내 정리됨).
3. 진짜 하드웨어 한계를 찾으려면 상한을 임시로 올리고(예: 방 200개) 같은 스크립트로 재측정. snap gap p99가 50ms를 크게 넘기 시작하는 지점이 서버 틱 포화점.
4. 측정 한계: 원격(RTT 183ms) 단일 지점, 프록시 경유. 봇은 서버가 생성(방당 봇 포함 4슬롯).
